# L1-L — Starter Pack, Bootstrap & Interface-Parity Model

## 1. Starter Pack boundary

The Adoption Starter Pack is a conforming implementation aid, not a second Canonical Core. It provides a discoverable path and reusable prompts/templates for establishing or deriving existing canonical objects and views.

Minimum Starter Pack coverage:

- OEB;
- Product/System Profile and Baseline references;
- AE Implementation Profile;
- Capability Bindings and readiness/gaps;
- identity, entitlement, OA/DA, policy and enforcement context;
- standards/practices applicability;
- architecture anchors/expectations;
- Context Requirements, durable knowledge and bootstrap;
- Evidence/Validation expectations;
- Engineering Health assessment/findings;
- derived capability-gap and health-gap views;
- normal implementation Plan structure;
- adoption Proof and Validation expectations.

The pack must not create Adoption Project, Adoption Plan, Installation Record, Conformance Claim, Environment Profile, Interface Profile, Capability Gap record, Health Assessment entity, or duplicate Validation identity.

## 2. START HERE contract

A fresh Human or agent must be able to answer from the distribution itself:

1. What is Agentic Engineering?
2. What exact release is this?
3. What is authoritative?
4. What is Starter/template/guidance?
5. What is reference/example only?
6. What baseline information must be supplied?
7. How is an organization-specific normal Plan derived?
8. How is adoption/conformance proven?
9. Where are Decision Records, ADRs, important experiments and learning?

No repository archaeology or hidden prior conversation is required.

## 3. Bootstrap Descriptor reuse

L1-L reuses the existing `Bootstrap Descriptor [B]` and L1-G context semantics. A conforming implementation must let a Human/agent resolve, where applicable:

- AE Implementation Profile / applicable Organization-specific implementation;
- exact Canonical AE Release;
- exact OEB revision;
- Product/System Profile and Baseline;
- active Loop, Contract, Plan, Increment/Task scope;
- architecture anchors;
- Context Requirements and durable sources;
- Capability Bindings and Access Paths;
- authenticated identity, entitlement, OA and relevant DA context;
- applicable policy and standards constraints;
- Evidence/Validation interfaces;
- durable state, Handoff and reconstruction paths.

## 4. Interface parity

> **Equivalent Canonical operations and governed state must be reachable; identical environment implementation is not required.**

The bootstrap/access mechanism may be a CLI, IDE integration, broker, API, agent host, remote service, Portal, local tooling, or another organization choice. None is required Canonical AE technology.

For each declared supported actor/runtime environment class, required agent-accessible operations must have a governed, deterministic, discoverable and proven access path.

Environment readiness is therefore a resolution/proof question, not an `Environment Profile` entity.

### Failure treatment

A missing discovery/interface/access path is surfaced through existing capability/readiness semantics as `BLOCK`, `CONSTRAIN`, or `DEGRADE` for the affected operation/scope. It is not routinely repaired by inserting a Human as clerical middleware.

Human judgment/Decision Authority remains legitimate; Human copying, clicking, uploading or translating after the substantive decision is already known is not a substitute for required agent-operability.

## 5. Interface-parity acceptance

L1-L reference Proof uses two materially different environments:

- containerized terminal/agent-runtime bootstrap;
- remote cloud workspace / IDE-mediated broker bootstrap.

They use different provider/IAM/UX mechanisms but resolve the same canonical governing state and required operations. Passing that proof resolves the broad issue #6 question at Canonical semantic level; future UX/product refinements remain implementation choices rather than a residual Canonical ambiguity.
